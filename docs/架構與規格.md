## 1. 技術架構

```
瀏覽器（React）
   │
   ▼
Cloudflare Worker（React Router v7 + Hono）
   ├─ 頁面 SSR：首頁、分類、商品頁（輸出 OG / JSON-LD）
   ├─ /api/*：商品、購物車、訂單、會員、後台
   ├─ /api/ecpay/*：綠界金流與物流的回呼（驗簽）
   │
   ├─ D1：會員、商品、規格庫存、訂單、進貨、設定
   ├─ R2：商品照片、分享圖（img.<網域>）
   └─ 外部服務：綠界（金流、物流）、Resend（Email）
```

- 機密資料（綠界 HashKey/HashIV、Resend API Key）只放在 Worker 的環境變數，不進 Git。
- 前後端共用 TypeScript 型別。

## 3. 會員與登入 ✅

**實作進度**：註冊、登入、登出、改姓名／手機、改密碼（其他裝置登出）已接 D1（`workers/api/auth.ts`、`app/lib/db/users.server.ts`）。🟡 需要寄信的部分（註冊驗證碼、忘記密碼、改 Email）等網域與寄信服務；在那之前所有會員視為已驗證，忘記密碼與改 Email 請客人私訊 IG。

### 3.1 方式：Email＋密碼（第一版只做這個）

- 第一版**不做** LINE、Google 登入。資料表保留 `auth_identities`，之後要加不用改結構。
- 驗證碼一律用 **6 位數驗證碼**，不用信件連結：客人常從 IG/LINE 內建瀏覽器進站，點信件連結會開在別的瀏覽器，接不回原本的畫面。

### 3.2 註冊

1. 填寫：姓名、Email、手機、密碼（至少 8 碼）。
2. Resend 寄 6 位數驗證碼 → 輸入 → 帳號啟用。
3. 尚未驗證 Email 可以逛、可以加購物車，**不能結帳**。

### 3.3 登入

- Email＋密碼。登入狀態保留 30 天，客人不必常常重新登入。
- 登入失敗不說是「帳號不存在」還是「密碼錯」，一律「Email 或密碼錯誤」。

### 3.4 忘記密碼

1. 輸入 Email → 畫面固定顯示「若此 Email 已註冊，驗證碼已寄出」（不透露是否有此帳號）。
2. 輸入驗證碼＋新密碼。
3. 改密碼後，**該帳號所有裝置強制登出**。

### 3.5 Email 用途

- 註冊驗證碼、忘記密碼驗證碼。
- 訂單成立、付款成功、出貨、取消通知。

### 3.6 規則與防護

- 密碼：WebCrypto PBKDF2-SHA256 雜湊加鹽（Workers 內建，不需另裝套件；迭代次數依 OWASP 建議設定）。
- Session：存 D1（只存 token 的 SHA-256），瀏覽器用 `HttpOnly; Secure; SameSite=Lax` cookie；後台可強制登出。
- 會員 API 只收 `application/json`（擋跨站表單）；註冊、登入同一 IP 每分鐘 10 次（Workers Rate Limiting）。🟡 Turnstile 之後再加。
- 驗證碼：10 分鐘有效、只存雜湊值、最多錯 5 次、同一 Email 60 秒內只能寄一次。
- 註冊、登入、忘記密碼都過 Cloudflare Turnstile，並限制頻率，避免機器人灌信把 Resend 每天 100 封的免費額度用完。
- 手機號碼：只檢查格式（09 開頭、10 碼），不做簡訊驗證。
- 會員中心可改姓名、手機、密碼；改 Email 要對新信箱重新驗證。

### 3.7 之後再評估

- **LINE 登入**：主要價值是之後用 LINE 官方帳號推播訂單通知。Email 權限要另外申請，客人也可能拒絕給，要補填流程。
- **Google 登入**：需在 Google Cloud 建 OAuth 用戶端與同意畫面；IG/LINE 內建瀏覽器會被 Google 擋。

## 4. 購物車 ✅

| 情境         | 行為                                                                                       |
| ------------ | ------------------------------------------------------------------------------------------ |
| 未登入       | 可逛、可加購物車，購物車存在瀏覽器（localStorage）                                         |
| 按「結帳」   | 跳出登入視窗，登入後回到結帳頁                                                             |
| 登入成功     | 瀏覽器購物車**合併**到會員購物車（同商品同規格數量相加，不超過庫存），合併後清掉瀏覽器暫存 |
| 已登入       | 購物車以伺服器（D1）為準                                                                   |
| **結帳完成** | **清掉瀏覽器暫存＋會員購物車**                                                             |
| 登出         | 清掉瀏覽器暫存                                                                             |

- **實作進度**：未登入（localStorage）、已登入（D1 `carts`，`/api/cart`）、登入時合併（`/api/cart/merge`，同商品同規格相加；現貨不超過庫存、客訂／代購上限 5 件）、登出清瀏覽器暫存 ✅。購物車頁的商品資料從 D1 讀（`/api/products`）。結帳清空等第 6 步。
- 🟡「結帳完成」的時間點：**訂單成立當下**就清空（商品已由訂單保留庫存）。信用卡付款失敗時，客人從訂單頁重新付款，不必回購物車重選。
- 🟡 多分頁同步：用 `storage` 事件／BroadcastChannel，其中一個分頁結帳完成，其他分頁的購物車也同步清空。
- 加購物車時檢查庫存；進結帳頁時再檢查一次，已售出的商品提示移除。
- 購物車頁顯示「再買 NT$xxx 免運」（門檻 NT$2,000，見 6.4）。

## 5. 商品、照片、分享預覽

### 5.1 商品

- 分類：包包、小皮件、飾品（首飾、圍巾、帽子等）、衣服褲子、鞋子、娃娃；預計加家飾。
- 規格（顏色、尺寸等）分開記庫存，3 件以下顯示「庫存偏低」（後台）。
- 完售商品**不刪除**：頁面改顯示「已售出」並推薦相似商品，保留搜尋流量。
- 🟡 現貨／客訂（代購）兩種型態，影響鑑賞期說明與到貨天數（見 9）。

### 5.1a 商品編號與網址 ✅

| 層級            | 給誰看              | 格式                                                                              | 範例                                                |
| --------------- | ------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------- |
| `id`            | 系統內部            | 自動遞增整數                                                                      | `14`                                                |
| `code` 商品編號 | 客人、IG 私訊、客服 | `AN` + 4 位流水號，上架時給定、永不重用；卡片顯示 No.0014                         | `AN0014`                                            |
| 網址            | Google、分享預覽    | `/products/<code 小寫>-<slug>`，以 code 為準；舊網址或描述打錯一律 301 到正式網址 | `/products/an0014-goyard-saint-sulpice-card-holder` |
| `sku`           | 後台庫存、進貨      | 品牌-分類-款式-顏色（規格層級）                                                   | `GOY-SLG-STSULPICE-BLK`                             |

- 商品編號不含分類意思，商品改分類不用換號；分類、顏色等意思放在 SKU。
- 後台新增的 SKU 自動產生：`品牌縮寫-分類-商品編號[-流水號]`，例：`GOY-SLG-AN0016-02`（款式、顏色是中文，無法自動縮寫）。改選項名稱以外的編輯沿用舊 SKU；刪掉的流水號不重用。

### 5.2 照片（R2）

- 後台上傳時在瀏覽器先壓縮：WebP（Safari 無法輸出 WebP 時用 JPEG），長邊 1600px；經 Worker（`PUT /api/admin/images`）存進 R2，鍵為 `products/<uuid>.webp`。壓縮後只有幾百 KB，不需要預簽網址。✅
- 照片網址目前是 `/img/<鍵>`（Worker 讀 R2）；接網域後改成 R2 自訂網域 `img.<網域>`，只改 `app/lib/images.ts`。
- 🟡 縮圖：之後再做。移除的照片只刪資料列，R2 檔案保留（之後排程清理）。
- 主圖另外產一張 **1200×630 JPG 分享圖**（LINE/FB 預覽不一定支援 WebP）。
- 一律使用自己拍的照片，不用品牌官方形象照。

### 5.3 分享預覽與 SEO ✅

- 商品頁伺服器端輸出：`og:title`（品牌＋品名）、`og:description`（價格、現貨/客訂）、`og:image`（完整網址）、`og:url`、`og:type=product`。
- JSON-LD `Product`（價格、幣別、是否有貨），讓 Google 搜尋結果顯示價格。
- sitemap.xml、canonical、真正的 404、圖片 alt。
- 改圖後 FB 用 Sharing Debugger 重抓；LINE 預覽有快取，更新會延遲。

## 6. 結帳、訂單、金流、物流

### 6.1 訂單狀態

```
待付款 ──付款成功──▶ 待出貨 ──出貨──▶ 已出貨 ──取貨/送達──▶ 已完成
   │                                     │
   └──逾時未付/取消──▶ 已取消             └──未取件/拒收──▶ 退回
```

- 狀態只能依上圖轉換，不能任意跳。
- 價格、運費、折扣**一律由後端重新計算**，不採用前端傳來的金額。

### 6.2 庫存

- 下單時用條件式扣庫存（`qty >= 下單數量` 才扣），防止一件商品被兩人買走。✅ 做法：訂單、明細、扣庫存、清購物車同一個交易，扣庫存靠 `product_variants` 的 `CHECK (stock >= 0)`，同時被買走時整筆失敗。
- 只有「現貨」扣庫存；客訂／代購（含部分現貨裡沒庫存的規格）下單後才採購，不扣。明細存 `kind_snapshot`，取消時依此放回。
- ATM、超商代碼這類「先成立訂單、後付款」：訂單保留庫存 🟡 **24–72 小時**，逾時自動取消並放回庫存。✅ 目前 ATM 72 小時、信用卡等 2 小時（`stock_hold_until`），Worker 排程每 15 分鐘取消逾時訂單（`expireOrders`）。
- 訂單編號：台灣日期 `YYMMDD`＋4 位亂數，例 `2610254821`（不用 AN 開頭，避免和商品編號混淆）。

### 6.3 金流（綠界全方位金流）🟡

| 付款方式                           | 備註                                                          |
| ---------------------------------- | ------------------------------------------------------------- |
| 信用卡一次付清                     | 開啟 3D 驗證                                                  |
| Apple Pay                          | 綠界頁面內                                                    |
| ATM 虛擬帳號                       | 綠界費率 1%/筆（未稅），最低 NT$10                            |
| 無卡分期（銀角零卡 Zingala／裕富） | 綠界 BNPL，不必另外串中租                                     |
| 超商代碼                           | ❓ 要不要開                                                   |
| LINE Pay                           | ❓ 原型有，需確認綠界全方位金流是否支援，否則要另串           |
| 貨到付款                           | ❓ 要不要開；若開，限金額上限＋**只有選貨到付款時做簡訊驗證** |

- 付款通知：每次驗簽（CheckMacValue）、比對金額、可重複接收不出錯（冪等）。
- 站內付 2.0（內嵌式）只開放特約會員，之後升級再評估。
- 綠界無官方 Node SDK，簽章與加解密自己寫；可用綠界 AI Skill 套件（github.com/ECPay/ecpay-api-skill）輔助。

### 6.4 物流（綠界物流整合，舊版 API）🟡

- 選舊版的原因：選門市前的畫面由我們自己設計，和網站風格一致；只有挑門市時跳到超商電子地圖。
- 超商：**7-ELEVEN、全家，C2C**（自己拿到門市寄）。萊爾富、OK 之後需要再加。
- 宅配：黑貓。
- 🟡 高單價商品**強制宅配**＋保價，超過門檻時結帳頁不顯示超商選項（門檻依超商商品價值上限與合約定）。
- 免運門檻：NT$2,000（原型設定）🟡。
- 出貨全程錄影。
- 貨態以綠界物流貨態代碼同步回訂單狀態。

### 6.5 通知

- 給客人（Email / Resend）：訂單成立、付款成功、出貨（附物流單號）、取消。
- 給店家：新訂單通知走 LINE 官方帳號 Messaging API（LINE Notify 已停止服務）或 Email。

## 7. 後台（沿用原型功能）

- **總覽**：今日訂單、待出貨、庫存偏低。
- **訂單**：狀態篩選、寄送與付款方式、物流單號、手動改狀態（依狀態流程）。✅ 已接 D1：取消、退回時現貨放回庫存（客訂／代購不放回，要賣再到庫存頁手動加）；每次改狀態記在 `order_events`；包材費存 `orders.pack_cost`。
- **商品**：上下架、規格、照片上傳、完售處理。✅ 已接 D1／R2（新品牌在商品表單直接輸入，存檔時建立）。
- **庫存**：± 盤點修正、低庫存門檻（`settings.low_stock_at`）已接 D1。
- **進貨**：外幣單價、匯率、刷卡手續費（1.5%）→ 換算台幣成本 → 入庫，算平均成本。
- **記帳簿／利潤**：每筆訂單淨利 = 售價 − 成本 − 金流手續費 − 包材費 − 實際運費。
- **設定**：各付款方式費率、包材費、運費成本、匯率。
- 🟡 每天自動匯出訂單與記帳到 Google Sheet 方便對帳（選配）。
- 後台登入（D16）：單一管理員，`/admin/login` 輸入密碼＋驗證器 App 的 6 位數碼；登入保留 7 天（HttpOnly cookie）；同一 IP 每分鐘 5 次；`/admin*` 與 `/api/admin*` 都在 Worker 檢查，未設定時一律擋。

## 9. 法規與營運 ⚠️

- **稅籍登記**：網路銷售月銷售額達 NT$10 萬須辦稅籍登記，並在網站揭露營業人名稱與統一編號。
- **發票**：免開發票只適用月銷售額 20 萬以下；超過需繳 5% 營業稅並開發票。結帳流程預留之後加發票欄位的彈性。
- **7 天鑑賞期**：
  - 現貨：適用，寫明退貨流程、運費負擔、退款天數。
  - 客訂／代購：只有「依消費者要求的客製化給付」且「事先告知」才能排除。❓ 先選好款上架、客人直接下單的情況可能不算，**需請教消保官或律師**。
  - 實作：加入購物車與結帳兩處說明，結帳勾選「已了解不適用 7 天鑑賞期」，同意紀錄存在訂單（`consent_no_return`）。
- **必備頁面**：賣家資訊、隱私權政策、服務條款、退換貨政策、運送說明、正品說明（貨源、配件、驗證方式）。
- 商標：描述商品可寫品牌名，不把品牌 Logo 當網站設計元素，不寫「授權經銷」。
- 反詐騙公告：頁尾與通知信註明「我們不會打電話要求你操作 ATM」。

## 11. 部署與 CI/CD 🟡

### 11.1 全部在 Cloudflare

| 項目                | 放在哪                                                   |
| ------------------- | -------------------------------------------------------- |
| 網域註冊、DNS、SSL  | Cloudflare Registrar / DNS（自動）                       |
| 前台＋後台頁面＋API | 同一個 Worker，綁 `<網域>`、`www.<網域>`                 |
| 照片                | R2，綁 `img.<網域>`                                      |
| 資料庫              | D1                                                       |
| 寄信                | Resend（DNS 加 SPF / DKIM 記錄，在 Cloudflare DNS 設定） |

### 11.2 環境：固定網址的 staging 🟡

| 環境    | 分支   | 網址                                       | 資料                                 |
| ------- | ------ | ------------------------------------------ | ------------------------------------ |
| 正式    | `main` | `<網域>`                                   | 正式 D1、正式 R2、綠界正式金鑰       |
| staging | `dev`  | `staging.<網域>`（Cloudflare Access 保護） | staging D1、staging R2、綠界測試金鑰 |
| 本機    | —      | localhost                                  | 本機 D1，跑種子資料                  |

- **為什麼 staging 要固定網址**：測試網址不會每個分支都變，Cloudflare Access 設一次就好；之後若加 LINE / Google 登入，它們的回呼網址要事先登記且不能用萬用字元，固定網址才能測。
- 做法：同一個 repo 在 Cloudflare 接**兩個 Worker**：`andelni`（正式）和 `andelni-staging`。Wrangler 設定檔用 `env.staging` 區塊綁 staging 的 D1 / R2 / 網域。
- staging 的資料：用種子腳本產生假商品、假會員，**不把正式客人的資料複製到 staging**（個資）。需要真實商品時只複製商品與照片。
- 機密（綠界 HashKey/HashIV、Resend）正式與 staging 各一組，用 `wrangler secret put [--env staging]` 或後台設定，不進 Git。
- 寄信：staging 只寄到自己的信箱（程式裡擋白名單），避免誤寄給真客人。

### 11.3 分支與流程

```
（選用）feature/xxx ──PR──▶ dev ──PR──▶ main
                           │            │
                   staging.<網域>     <網域>
```

1. 一般開發：直接在 `dev` 或開 `feature/xxx` 再合回 `dev`。push 後 GitHub Actions 跑檢查，Workers Builds 部署到 staging（含套用 staging 的 D1 migration）。
2. 在 staging 跑「上線前測試清單」（11.6）。
3. 開 PR：`dev` → `main`，CI 通過才能 merge。
4. merge 後 Workers Builds 套用正式 D1 migration → 部署正式站。migration 已經在 staging 跑過一次。
5. 緊急修正：從 `main` 開 `hotfix/xxx` → PR 回 `main` → 上線後把 `main` 合回 `dev`，避免兩邊分岔。
6. 每次上正式站打 tag（`v2026.10.19` 之類），出問題時知道要回到哪一版；Worker 可在後台一鍵回滾到前一個版本。

### 11.4 設定 ✅

> 建置用 `@cloudflare/vite-plugin`：環境在**建置時**決定（`CLOUDFLARE_ENV=staging`），`wrangler deploy` 會自動部署到該環境。
> ⚠️ `wrangler d1 migrations apply` **不會**跟著 build 切環境，一律明確寫 `--config wrangler.jsonc`（staging 再加 `--env staging`），否則會套到正式 D1。

- **Workers Builds：`andelni`（正式）**
  - Production branch：`main`
  - Build command：`pnpm build`
  - Deploy command：`npx wrangler d1 migrations apply DB --remote --config wrangler.jsonc && npx wrangler deploy`
  - 建置環境變數：`VITE_SITE_URL=https://<網域>`（掛網域後）
  - 非正式分支建置：關閉
- **Workers Builds：`andelni-staging`**
  - Production branch：`dev`
  - Build command：`pnpm build`
  - Deploy command：`npx wrangler d1 migrations apply DB --remote --config wrangler.jsonc --env staging && npx wrangler deploy`
  - 建置環境變數：`CLOUDFLARE_ENV=staging`
  - 非正式分支建置：🟡 選用，`feature/*` 可開預覽網址看畫面（預覽上登入功能不能用）
- **手動部署**（Workers Builds 接好前）：`pnpm deploy:staging`、`pnpm run deploy`（正式）。
- **D1**：`andelni`（正式）、`andelni-staging`；位置 APAC。staging 用 `pnpm db:seed:staging` 放示範資料，正式站不放假資料。
- **GitHub Actions**（`.github/workflows/ci.yml`）：`pnpm install --frozen-lockfile` → typecheck → lint → test → format check。不負責部署。
- GitHub 分支保護：`main` 只能從 PR merge 且必須通過 CI；`dev` 必須通過 CI。

### 11.5 資料庫 migration 規則

- 每次改資料表都新增一個 migration 檔（`migrations/0001_init.sql`、`0002_xxx.sql`），不修改已套用過的檔。
- 只做「向前相容」的變更：先加欄位、程式改完上線，再另一次刪舊欄位。因為 migration 先跑、新程式後上線，中間舊程式仍在服務。
- migration 出錯時可用 D1 時間回溯還原（付費版可回溯 30 天、免費版 7 天）。

### 11.6 上線前測試清單（在 staging 跑）

- [ ] 註冊 → Email 驗證碼 → 登入；未驗證不能結帳
- [ ] 忘記密碼 → 驗證碼 → 重設 → 其他裝置被登出
- [ ] 未登入加購物車 → 登入後合併 → 結帳完成後購物車清空（含其他分頁）
- [ ] 信用卡、ATM、無卡分期（綠界測試環境）付款成功與失敗
- [ ] ATM 逾時未付 → 自動取消、庫存放回
- [ ] 超商電子地圖選門市 → 建物流單 → 貨態回傳
- [ ] 通知信：訂單成立、付款成功、出貨
- [ ] 商品頁貼到 LINE 的分享預覽
- [ ] 後台：上架、改庫存、進貨、出貨
